## 1. Что это за система

Внутренняя CRM для компании, занимающейся строительством модульных домов. Команда до 10 человек. Каждый проект — индивидуальный (типовых готовых моделей нет, только шаблоны-заготовки по количеству модулей).

Главная задача системы — автоматизация полного цикла от лида до сдачи дома, с особым акцентом на **переговорный процесс с клиентом**: менеджер в разговоре должен видеть, как меняется цена при каждой правке, и объяснять клиенту "что почём".

Хоститься будет локально (внутренний сервер компании).

## 2. Роли пользователей

- **Менеджер** — продаёт, общается с клиентом, ведёт сделку от лида до договора. Работает в CRM большую часть дня.
- **Проектировщик** — рисует проекты в ArchiCAD, отправляет расчёты и PDF-планы в CRM через плагин. Коммерческие данные не видит.
- **Производство** — файловая роль для производственных материалов; по текущим правилам доступа не работает с коммерческими полями.
- **Админ** — редактирует справочники (позиции, цены, пользователи) через Django admin.
- **Руководитель** — видит всю воронку, аналитику, может править любые сделки.

## 3. Ключевые концепции

### Проект, сделка, версия
- **Deal (Сделка)** — основная сущность. Один клиент — одна сделка. Имеет `project_code` вида `3МД-Иван-Пулково` (уникальный бизнес-ключ; нормализованная копия используется для поиска и защиты от дублей).
- **ProjectVersion (Версия проекта)** — итерация расчёта. Каждая сделка имеет много версий, каждая версия — иммутабельный снэпшот конфигурации и цен на момент отправки клиенту.
- **Client (Клиент)** — физлицо или компания, заказчик.

### Количество модулей
Метка "3МД", "5МД", "7МД" и т.д. означает количество модулей в доме. Хранится как простое число `module_count` на Deal. Это **не** ссылка на каталог моделей — каталога нет, каждый дом индивидуальный. Используется только для фильтрации и аналитики.

Ограничения отличаются по входу:
- модель и UI допускают `0..15` (`0` нужен для черновых/неполных сделок);
- API плагина принимает только `1..15`, потому что отправка ArchiCAD должна описывать реальный проект.

### Интеграция с ArchiCAD
Плагин ArchiCAD (пишется отдельно на C++) подключается к CRM по REST API. Отправляет:
- Структурированный payload (JSON) — список объектов дома: стены, окна, двери, полы, зоны, кровля с их guid'ами и параметрами
- Имя PDF-плана (`plan_pdf_filename`), если файл уже должен лежать в файловом хранилище версии. Текущий endpoint не принимает multipart upload.

Каждая отправка создаёт новую `ProjectVersion`. Плагин шлёт детально (по объектам с guid'ами), а не суммарно, чтобы можно было показать **детальный diff** между версиями. На текущем этапе API сохраняет payload в `ProjectVersion.frozen_data`; автоматический объектный diff остаётся целевым поведением и не должен считаться реализованным без проверки кода.

### Версионирование и diff
Целевое поведение: когда приходит новая версия, сервер сравнивает её с предыдущей **по guid'ам объектов**. Выделяет изменения:
- Объект изменён (размер, тип) → модификация
- Объект добавлен → новый
- Объект удалён → убран

Каждое изменение должно превращаться в стоимостную разницу ("окно W-02 уменьшилось с 2100×2300 на 1800×2300 → -45 000 ₽"). Это критичная фича системы — "что почём", но автоматический diff и расчёт дельт ещё не являются гарантированным поведением текущего endpoint.

### Источник данных в полях
Каждое поле в конфигураторе имеет источник:
- `archicad` — прилетело из плагина, не трогалось
- `manual` — ввёл менеджер (цены от поставщиков, сауна)
- `override` — прилетело из ArchiCAD, но менеджер переписал

В UI источник показывается иконкой рядом с полем. Менеджер может редактировать любое поле.

### Отправка КП клиенту
Целевой workflow, когда менеджер жмёт "Зафиксировать и отправить":
1. Текущая draft-версия фиксируется со статусом `sent_to_client`
2. Генерируется итоговый PDF: титулка + план из ArchiCAD + таблица расчёта
3. Автоматически создаётся новая draft-версия (копия отправленной) для дальнейшей работы
4. Отправленная версия больше не редактируется (хранится в истории)

Текущий код хранит статусы и поля `quote_pdf_path` / `quote_sent_at`, но строгая иммутабельность и генерация КП ещё отмечены как незавершённые в `TODO.md`.

### Наценка
Хранится как параметр (% на Deal), применяется при расчёте итога. Не зашита в формулы.

## 5. Стек

- **Backend:** Django + Django REST Framework. `requirements.txt` сейчас закрепляет диапазон `Django>=5,<6`; `core/settings.py` был сгенерирован Django 6.0.4, поэтому фактический runtime нужно сверять при обновлении зависимостей.
- **DB:** PostgreSQL 16
- **Realtime:** Django Channels + Redis (`REDIS_URL`) для WebSocket-событий.
- **Frontend:** Django templates + HTMX + Alpine.js/Bootstrap для интерактивности.
- **Файловое хранилище:** локальная папка `CRM_FILES_ROOT` (по умолчанию `crm_files` в корне проекта); пути в БД относительные.
- **Аутентификация:** Django стандартная для людей, DRF token для плагина.
- **Деплой:** текущий Docker Compose поднимает `app` (Daphne), `db` (Postgres) и `redis`. Nginx/certbot — внешний слой, если он нужен в конкретной установке.

## 6. Ключевые бизнес-правила (что легко забыть)

1. `project_code` — уникальный, регистронезависимый для поиска. Формат, который строит код: `{модули}МД-{клиент}-{участок}`.
2. `module_count` — целое число `0..15` в модели/UI и `1..15` в API плагина. Не ссылка на каталог.
3. Каждая отправка из ArchiCAD = новая ProjectVersion. Всегда.
4. После отправки КП клиенту текущая draft замораживается, автоматически создаётся новая draft.
5. Замороженные версии (status != draft) должны быть **иммутабельны**. Это бизнес-правило пока требует технического enforcement.
6. Плагин не шлёт мебель — только конструктив, который влияет на цену.
7. Все цены при создании ProjectVersion копируются снэпшотом в frozen_data. Изменение CostItem в будущем **не меняет** старые версии.
8. Наценка — параметр на Deal, не в формуле.
9. Все роли видят разные наборы полей — проектировщик не видит коммерцию, менеджер не правит чужие сделки.
