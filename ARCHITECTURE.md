# ARCHITECTURE.md

Этот документ — контекст для AI-ассистентов (Cursor, Claude Code) и для разработчика. Кладётся в корень репозитория. В начале каждой сессии с AI добавляй этот файл в контекст.

## 1. Что это за система

Внутренняя CRM для компании, занимающейся строительством модульных домов. Команда до 10 человек. Каждый проект — индивидуальный (типовых готовых моделей нет, только шаблоны-заготовки по количеству модулей).

Главная задача системы — автоматизация полного цикла от лида до сдачи дома, с особым акцентом на **переговорный процесс с клиентом**: менеджер в разговоре должен видеть, как меняется цена при каждой правке, и объяснять клиенту "что почём".

Хостинг — **облачный VPS** (CRM + Postgres + Redis + умный умник). Офисный ПК с `D:\Общая_Рабочая` остаётся только **индексатором архива**: он не отвечает на поиск из CRM.

## 2. Роли пользователей

- **Менеджер** — продаёт, общается с клиентом, ведёт сделку от лида до договора. Работает в CRM большую часть дня.
- **Проектировщик** — рисует проекты в ArchiCAD, отправляет расчёты и PDF-планы в CRM через плагин. Коммерческие данные не видит.
- **Админ** — редактирует справочники (позиции, цены, пользователи) через Django admin. Это роль сотрудника, не владелец системы.
- **Руководитель** — видит всю воронку, аналитику, может править любые сделки.
- **Superadmin** — скрытая роль владельца системы. Назначается только командой `ensure_superadmin`, в разделе «Сотрудники» не показывается и не выдаётся.

## 3. Ключевые концепции

### Проект, сделка, версия
- **Deal (Сделка)** — основная сущность. Один клиент — одна сделка. Имеет `project_code` вида "3МД Иванов Пулково" (уникальный бизнес-ключ).
- **ProjectVersion (Версия проекта)** — итерация расчёта. Каждая сделка имеет много версий, каждая версия — иммутабельный снэпшот конфигурации и цен на момент отправки клиенту.
- **Client (Клиент)** — физлицо или компания, заказчик.

### Количество модулей
Метка "3МД", "5МД", "7МД" и т.д. означает количество модулей в доме (от 1 до ~15, рекорд 11). Хранится как простое число `module_count` на Deal. Это **не** ссылка на каталог моделей — каталога нет, каждый дом индивидуальный. Используется только для фильтрации и аналитики.

### Интеграция с ArchiCAD
Плагин ArchiCAD (пишется отдельно на C++) подключается к CRM по REST API. Отправляет:
- Структурированный payload (JSON) — список объектов дома: стены, окна, двери, полы, зоны, кровля с их guid'ами и параметрами
- PDF с планом этажа (один файл, одна страница)

Каждая отправка создаёт новую `ProjectVersion`. Плагин шлёт детально (по объектам с guid'ами), а не суммарно, чтобы можно было показать **детальный diff** между версиями.

### Версионирование и diff
Когда приходит новая версия, сервер сравнивает её с предыдущей **по guid'ам объектов**. Выделяет изменения:
- Объект изменён (размер, тип) → модификация
- Объект добавлен → новый
- Объект удалён → убран

Каждое изменение автоматически превращается в стоимостную разницу ("окно W-02 уменьшилось с 2100×2300 на 1800×2300 → -45 000 ₽"). Это критичная фича системы — "что почём".

### Источник данных в полях
Каждое поле в конфигураторе имеет источник:
- `archicad` — прилетело из плагина, не трогалось
- `manual` — ввёл менеджер (цены от поставщиков, сауна)
- `override` — прилетело из ArchiCAD, но менеджер переписал

В UI источник показывается иконкой рядом с полем. Менеджер может редактировать любое поле.

### Отправка КП клиенту
Когда менеджер жмёт "Зафиксировать и отправить":
1. Текущая draft-версия фиксируется со статусом `sent_to_client`
2. Генерируется итоговый PDF: титулка + план из ArchiCAD + таблица расчёта
3. Автоматически создаётся новая draft-версия (копия отправленной) для дальнейшей работы
4. Отправленная версия больше не редактируется (хранится в истории)

### Наценка
Хранится как параметр (% на Deal), применяется при расчёте итога. Не зашита в формулы.

### Цена, которую видит менеджер сейчас
Автосмета на карточке выключена. Рабочая сумма — `Deal.agreed_price` («Договорная цена»), её вводят вручную. Флаг `CONFIGURATOR_ENABLED` в `deals/views.py` по умолчанию `False` и из окружения не читается. Формулы `calculate_config` и справочник `CostItem` при этом сохранении не участвуют. Список сделок для руководства показывает итог последней версии из `frozen_data`, а не договорную цену. Операционные правила: `docs/agreed-price.md`.

Текст выше про конфигуратор, фиксацию КП и иммутабельность отправленной версии описывает целевой контур. В текущих шаблонах кнопки «Зафиксировать и отправить» нет. В блоке согласований кнопка «Отправить клиенту» только ставит версии статус `sent_to_client` и `quote_sent_at`: PDF не собирается, новая draft-копия не создаётся, статус можно вернуть в черновик.

## 5. Стек

- **Backend:** Django 5 + Django REST Framework (для API плагина)
- **DB:** PostgreSQL 16
- **Frontend:** Django templates + HTMX + Alpine.js для интерактивности на старте. Конфигуратор с живым пересчётом возможно переедет на React (решаем в фазе 5).
- **Файлы сделок и заказчиков:** объектное хранилище S3 (`ch-crm-files`). Локальный диск CRM — только кэш/временные файлы, не источник правды.
- **Аутентификация:** Django стандартная для людей, DRF token для плагина.
- **Деплой:** Docker Compose на облачном VPS (app + Postgres + Redis + telegram-бот + nginx + HTTPS). Умный умник — **systemd на хосте**, не контейнер.

### Архив планировок: два умника

PDF архива (`D:\Общая_Рабочая`, сотни ГБ) **не едут в облако**. В облако уезжает только **индекс** (SQLite-каталог + Chroma). Поиск и чат работают по индексу.

| Роль | Где | `UMNIK_ROLE` | Что делает | Чего не делает |
|------|-----|--------------|------------|----------------|
| **Индексатор** | офисный ПК у шары `D:\Общая_Рабочая` | `indexer` | Смотрит PDF, эмбеддинги, таблицы комнат/м², сам публикует снимок индекса в S3 | Не обслуживает поиск CRM, не чат, не lookup |
| **Умный умник** | тот же облачный VPS, что и CRM | `query` | Тянет индекс из S3, отвечает на lookup/чат/поиск | Не сканирует офисную шару, не строит эмбеддинги заново |

```
D:\Общая_Рабочая  →  умник-индексатор (офис)
                         │  каждые ~5 мин, если индекс изменился
                         ▼
              S3  ch-crm-umnik-index/   (catalog.db + chroma, сотни МБ)
                         │
                         ▼
              умный умник (VPS)  ←── CRM  GET /crm/lookup
                                     └── CRM  POST /crm/chat
```

- CRM **всегда** ходит только в облачный умник: `UMNIK_URL` = query-сервис на VPS. Офисный индексатор в `UMNIK_URL` не указывают.
- Lookup: `GET {UMNIK_URL}/crm/lookup?query=...` с `Authorization: Bearer {UMNIK_TOKEN}`. Ответ — комнаты и м² из таблиц индекса. OpenRouter из CRM не вызывается.
- Если query-умник не отвечает, сделка открывается как обычно — блок архива показывает заглушку.
- Писать в архив PDF из CRM нельзя. Индексатор тоже в архив не пишет — только читает шару.
- Чат умника в UI виден любому вошедшему сотруднику: `POST {UMNIK_URL}/crm/chat`. Поиск проектов в чате — по индексу на сервере, не через офисный Qwen.
- **Владелец системы** — роль `superadmin` **или** Django `is_superuser`. Логин `admin` и роль `admin` владельца не дают. Учётка создаётся командой `ensure_superadmin` (логин по умолчанию `PLATFORM_OWNER_USERNAME=superadmin`). Только владелец правит код CRM через чат, видит кнопку «Перезапустить CRM» и может вызвать `restart_crm` (`docker compose restart app`, не db/redis/умник).
- Обратный вызов умника в CRM: `/api/umnik/deals/` с тем же `UMNIK_TOKEN` и заголовком `X-Umnik-Actor`. Так меняются статус, наценка, конфигуратор и суммы; запись в журнал изменений идёт от имени актора.

**Снимок индекса** — каталог `umnik/data/pdf_archive/` (`catalog.db` + FTS + `layout_sheets`/`layout_rooms` + `chroma/`). Это не PDF. Публикация: после успешного sync индексатор checkpoint SQLite, пакует каталог, заливает `manifest.json` + `latest.tar.gz` в бакет. Query-умник сравнивает generation и подменяет локальную копию атомарно.

**Оригиналы PDF** остаются в офисе. Поиск, карточка сделки и чат работают по извлечённому тексту, эмбеддингам и таблицам. Скачать сам чертёж с VPS нельзя, пока отдельно не решим зеркалировать выбранные PDF в `ch-crm-files`.

Режим `UMNIK_ROLE=local` — только разработка: индекс на том же компьютере, без S3, как раньше. В проде не используется.

### Облачный хостинг (прод)

Один VPS Cloud.ru: **4 vCPU / 16 ГБ RAM / 120 ГБ SSD**. Docker: Django/Daphne, Postgres 16, Redis 7, telegram-бот. Query-умник — процесс на хосте (`systemd`, порт 7861, в группу безопасности не открываем). CRM в контейнере ходит на `http://host.docker.internal:7861`.

Публичный веб CRM — порт **9090** (`http://<public-ip>:9090`). Он уже открыт в группе безопасности `SSH-access_ru.AZ-1`. Пока без своего домена и TLS на 443. Локальная разработка остаётся на `8001`. Кабинет заказчика на том же порте: `/deals/<id>/client-portal/`. Отдельный порт не нужен.

### Кабинет заказчика (без почты)

Почта для клиентов **не используется** (ограничения Роскомнадзора): нет OTP, нет писем со ссылкой, SMTP для кабинета не настраиваем.

У каждого клиента свои **ID для входа и пароль**:
- **ID для входа** — отдельный номер (`Client.portal_login_id`, например 100013), не внутренний № карточки. Видно в списке клиентов и в блоке «Вход в кабинет» на карточке. Можно сменить.
- **Пароль** — задаёт менеджер в карточке клиента или при создании сделки.

Заказчик открывает ссылку кабинета и вводит ID + пароль. Email в карточке, если заполнен, только справочный (договоры), не логин.

S3 — один бакет **`ch-crm`** (Cloud.ru Object Storage, endpoint `https://s3.cloud.ru`, регион `ru-central-1`):

| Префикс | Состав |
|---------|--------|
| `files/` | файлы заказчиков и сделок: `clients/{id}-{имя}/projects/...` |
| `umnik-index/` | снимки векторного индекса архива |
| `backups/` | дампы Postgres |

Бакет приватный. Access Key ID в формате `<tenant_id>:<key_id>`. Клиенту файлы — signed URL. Версионирование объектов включено.

## 6. Ключевые бизнес-правила (что легко забыть)

1. `project_code` — уникальный, регистронезависимый для поиска. Формат "{модули}МД {Фамилия} {Локация}".
2. `module_count` — целое число 1..15. Не ссылка на каталог.
3. Каждая отправка из ArchiCAD = новая ProjectVersion. Всегда.
4. После отправки КП клиенту текущая draft замораживается, автоматически создаётся новая draft.
5. Замороженные версии (status != draft) **иммутабельны**. Никогда не редактируются.
6. Плагин не шлёт мебель — только конструктив, который влияет на цену.
7. Все цены при создании ProjectVersion копируются снэпшотом в frozen_data. Изменение CostItem в будущем **не меняет** старые версии.
8. Наценка — параметр на Deal, не в формуле.
9. Все роли видят разные наборы полей — проектировщик не видит коммерцию, менеджер не правит чужие сделки.
10. Кабинет заказчика: вход только **ID для входа + пароль**. Почту, OTP и коды на email не шлём.
