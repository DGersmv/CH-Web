# IMPLEMENTATION_PLAN.md

Пошаговый план реализации CRM. Начинается с фундамента, движется к работающему dashboard менеджера. Конфигуратор и API плагина — следующие фазы, здесь не описаны.

**Как пользоваться:**
- Задачи выполняются по порядку. Не прыгай вперёд.
- Каждая задача заканчивается коммитом в git.
- После задачи — прогони её блок "Проверить". Не переходи к следующей, пока эта не работает.
- "НЕ делать пока" — это спасение от преждевременной оптимизации.

**Оценка времени** — для человека с базой веб-разработки, работающего с AI-помощью, в режиме 3-4 часа в день.

## ФАЗА 0 — Фундамент проекта

Цель: запустить Django с Postgres в Docker, увидеть "hello world" в браузере после логина.

### Задача 0.1 — Инициализация репозитория

**Что делаем:**
- Создать git-репозиторий
- Файлы: `.gitignore` (Python, Django, JetBrains/VSCode), `README.md` (2 строки — название и что делает), `ARCHITECTURE.md` (положить готовый)

**Проверить:** `git init && git add . && git commit -m "initial"` работает без ошибок.

**НЕ делать пока:** CI/CD, GitHub Actions, сложные hooks.

---

### Задача 0.2 — Docker Compose скелет

**Что делаем:**
- `docker-compose.yml` с двумя сервисами: `db` (postgres:16) и `app` (python:3.12-slim)
- `Dockerfile` для `app` — простой, без multi-stage
- `.env.example` с переменными: `DJANGO_SECRET_KEY`, `POSTGRES_*`, `DEBUG=True`
- `requirements.txt` с: Django, psycopg[binary], python-dotenv

**Почему:** запускать всё локально без Docker — это каша из версий Python и Postgres. Docker даёт воспроизводимое окружение сразу.

**Проверить:** `docker compose up db` стартует Postgres, `docker compose run app python --version` показывает 3.12.

**НЕ делать пока:** nginx, HTTPS, prod-настройки, Redis, Celery.

---

### Задача 0.3 — Django проект

**Что делаем:**
- Внутри контейнера: `django-admin startproject core .` (структура проекта)
- Настройка `DATABASES` на Postgres из переменных окружения
- Первая миграция: `python manage.py migrate`
- Создать суперюзера
- Запустить `runserver` на 0.0.0.0:8000

**Проверить:** открывается `http://localhost:8000/admin/`, логин работает, видно стандартную Django-админку.

**НЕ делать пока:** никаких приложений (`apps`), кастомных user-моделей — это следующая задача.

---

### Задача 0.4 — Кастомная User-модель с ролями

**Что делаем:**
- Создать app `accounts`: `python manage.py startapp accounts`
- Модель `User` на базе `AbstractUser` с полем `role` (choices: manager / designer / admin / head)
- Подключить как `AUTH_USER_MODEL` в settings — **обязательно до первой миграции прикладных моделей**, иначе потом переделывать больно
- Зарегистрировать в админке, чтобы при создании юзера можно было выбрать роль

**Почему критично сейчас:** расширять `User` в Django после первой миграции — это отдельный цирк. Делаем сразу.

**Проверить:** в админке при создании пользователя виден dropdown role. Создай себе пользователя с role=admin.

**НЕ делать пока:** права доступа, группы, permissions — это всё в Фазе 1.

---

### Задача 0.5 — Главная страница "hello world" за логином

**Что делаем:**

**Проверить:** без логина → редирект на /accounts/login/. После логина → видно "Добро пожаловать, имя".

**НЕ делать пока:** красивый дизайн, Bootstrap, навигационное меню, footer.

**Конец Фазы 0.** У тебя есть работающее Django-приложение в Docker с Postgres, с собственной моделью юзера, с защищённой главной страницей. Всё в git.

## ФАЗА 1 — Модели данных и админка

Цель: все основные сущности (Client, Deal, ProjectVersion, Task, CostItem) созданы и редактируются через Django admin. Сюда вбиваешь тестовые данные, на которых потом работает dashboard.

### Задача 1.1 — App `clients` и модель Client

**Что делаем:**
- `python manage.py startapp clients`
- Модель `Client`: full_name, phone, email, location (текстовое поле — адрес участка), notes (TextField), created_at, created_by (FK → User).
- Регистрация в админке с list_display, search_fields.

**Проверить:** в админке можно создать 3-4 тестовых клиента. Поиск работает.

**НЕ делать пока:** история изменений, интеграция с телефонией, дубль-детекция.

---

### Задача 1.2 — App `deals` и модель Deal

**Что делаем:**
- Модель `Deal`:
  - `project_code` (CharField, unique, max_length=200)
  - `project_code_normalized` (CharField, db_index, unique) — заполняется автоматически в `save()` методом нормализации (lowercase, strip, collapse spaces)
  - `module_count` (PositiveSmallIntegerField, 1..15 — валидатор)
  - `client` (FK → Client, null=True, blank=True — для orphan)
  - `status` (CharField с choices: orphan / new / qualified / sent_quote / contract / prepayment / production / installation / delivered / lost)
  - `assigned_manager` (FK → User, null=True)
  - `margin_percent` (DecimalField, default=30)
  - `created_at`, `updated_at`
- Миграция, админка с удобными filters и list_display.

**Проверить:** создай через админку 5-6 сделок на разных стадиях, разного module_count, с привязанными клиентами. `project_code_normalized` заполняется автоматически.

**НЕ делать пока:** ProjectVersion (следующая задача), UI для менеджера, Kanban.

---

### Задача 1.3 — Модель ProjectVersion (скелет)

**Что делаем:**
- Модель `ProjectVersion`:
  - `deal` (FK), `version_number` (PositiveIntegerField), `source` (choices), `status` (choices)
  - `frozen_data` (JSONField) — пока null=True, заполнишь позже
  - `plan_pdf_path`, `plan_preview_png_path`, `plan_uploaded_at` — все nullable (пока PDF не приходит)
  - `quote_pdf_path`, `quote_sent_at` — nullable
  - `created_by` (FK → User), `created_at`
- Unique together: `(deal, version_number)`
- Админка с inline в Deal (чтобы у сделки было видно список версий)
- Простая функция `deal.create_new_version(source='manual')` — создаёт следующую версию с правильным номером

**Проверить:** у тестовой сделки создал через админку 2-3 версии, видны в inline под сделкой.

**НЕ делать пока:** реальное содержимое frozen_data, загрузку PDF, генерацию quote_pdf, иммутабельность — всё это для Фазы 5 (конфигуратор). Сейчас это просто записи в БД.

---

### Задача 1.4 — Модель Task (задачи менеджера)

**Что делаем:**
- Модель `Task`: `deal` (FK, nullable — задача может быть не привязана к сделке), `assignee` (FK → User), `title` (CharField), `due_date` (DateField), `is_done` (BooleanField, default=False), `completed_at` (DateTimeField, nullable), `created_at`
- Админка стандартная
- Метод `mark_done()` — ставит is_done=True и completed_at=now()

**Проверить:** создай 5-7 задач на разные даты (некоторые просрочены), на разных сделках.

**НЕ делать пока:** напоминания на email, повторяющиеся задачи, приоритеты, теги.

---

### Задача 1.5 — Модель CostItem (справочник)

**Что делаем:**
- Модель `CostItem`: `code` (unique), `name_ru`, `unit` (choices: sqm, lm, pcs, complex, rubles), `category` (choices: floors, walls, openings, roof, bathroom, engineering, overhead, additional), `price_material` (Decimal), `price_work` (Decimal), `formula_multiplier` (CharField, nullable — пока не используется), `is_active` (bool, default=True)
- Админка с фильтром по category, поиском по name, сортировкой

**Проверить:** вбей в админку первые 5-10 позиций из Excel (пол 150мм, пол 200мм, ламинат, и т.д.) — это тестовые данные для будущего конфигуратора.

**НЕ делать пока:** импорт из Excel автоматом (сделаем позже отдельным скриптом), валидация формул.

---

### Задача 1.6 — Модель ChangeLog (журнал изменений)

**Что делаем:**
- Модель `ChangeLog`: `project_version` (FK), `changed_by` (FK → User), `changed_at` (auto_now_add), `field_path` (CharField), `old_value` (JSONField), `new_value` (JSONField)
- Пока — только модель и админка, без автоматической записи (триггеры добавим в фазе конфигуратора)

**Проверить:** через админку можно вручную создать запись ChangeLog и увидеть её.

**НЕ делать пока:** автоматическое логирование при изменениях — это в Фазе 5.

**Конец Фазы 1.** Все базовые сущности есть в БД и редактируются через Django admin. В админке ты набил тестовые данные (5-6 сделок, 10-15 задач, 10 позиций каталога). Теперь есть из чего строить dashboard.

## ФАЗА 3 — Интерактивность: задачи, стадии, редактирование

Цель: менеджер не только смотрит, но и работает в системе: выполняет задачи, меняет стадии сделок, редактирует простые поля.

### Задача 3.1 — Отметить задачу выполненной

**Что делаем:**
- В списке задач и на карточке сделки рядом с каждой задачей — чекбокс
- При клике по чекбоксу — POST-запрос через HTMX на endpoint `/tasks/{id}/toggle/`, возвращает обновлённую строку
- Выполненные задачи показываются зачёркнутыми внизу списка, с possibility раскрыть/скрыть

**Почему HTMX:** чекбокс должен работать без перезагрузки страницы. HTMX это даёт в 5 строк. Пока везде SPA не нужен.

**Проверить:** кликаешь галочку — задача зачёркивается, страница не перезагружается.

**НЕ делать пока:** drag-drop задач между днями, снятие галочки обратно (пусть пока — только в одну сторону), повторяющиеся задачи.

---

### Задача 3.2 — Добавить новую задачу к сделке

**Что делаем:**
- На карточке сделки кнопка "+ Задача"
- По клику — модальное окно (Bootstrap modal) с формой: title, due_date, assignee (дефолт — текущий пользователь)
- Отправка через HTMX, обновление списка задач на странице

**Проверить:** добавил задачу из карточки сделки — она появилась в списке.

**НЕ делать пока:** шаблоны задач, batch-добавление, загрузка вложений.

---

### Задача 3.3 — Смена стадии сделки

**Что делаем:**
- На карточке сделки — dropdown для смены status
- При смене — POST через HTMX, обновление бейджа
- Запись в ChangeLog: field_path="status", old_value, new_value, user, timestamp

**Почему ChangeLog:** позже этот журнал будет показываться в UI. Начинаем собирать данные сразу.

**Проверить:** сменил стадию — бейдж обновился, запись в ChangeLog появилась (проверь через админку).

**НЕ делать пока:** Kanban-доска (это отдельный screen в будущем), бизнес-правила переходов (нельзя из "new" прыгнуть в "delivered").

---

### Задача 3.4 — Быстрое редактирование менеджера и наценки

**Что делаем:**
- На карточке сделки два поля с inline-редактированием:
  - `assigned_manager` (dropdown)
  - `margin_percent` (числовое поле)
- Клик по значению → превращается в input → blur → сохранение
- Пишется в ChangeLog

**Проверить:** поменял менеджера на другого, поменял наценку с 30 на 25 — сохраняется, отображается.

**НЕ делать пока:** редактирование сложных полей (project_code), клиента, module_count — это должно идти через отдельные формы с предупреждением ("вы меняете ключевое поле").

---

### Задача 3.5 — Создание сделки вручную

**Что делаем:**
- На `/deals/` кнопка "+ Новая сделка"
- Форма: project_code, module_count, client (с возможностью создать нового тут же), assigned_manager
- При создании валидация project_code (уникальность, формат)
- После создания → редирект на карточку новой сделки

**Проверить:** создал сделку — появилась в списке и в Postgres.

**НЕ делать пока:** дубль-проверка "похожих" сделок, импорт из CSV, интеграция с лид-формой сайта.

**Конец Фазы 3.** Менеджер может полноценно работать со сделками — создавать, редактировать ключевые поля, вести задачи, менять стадии. Dashboard стал интерактивным.

### Задача 4.5 — Глобальный поиск в шапке

**Что делаем:**

## Приложение: команды, которые понадобятся часто

```bash
# Запустить всё
docker compose up -d

# Логи приложения
docker compose logs -f app

# Зайти в контейнер приложения
docker compose exec app bash

# Миграции
docker compose exec app python manage.py makemigrations
docker compose exec app python manage.py migrate

# Суперюзер
docker compose exec app python manage.py createsuperuser

# Shell для отладки
docker compose exec app python manage.py shell

# Тесты
docker compose exec app python manage.py test
```

Положи это как alias в `Makefile` после Фазы 0 — сэкономишь время.
