# Архив планировок: поиск из CRM

CRM показывает комнаты и площади из индекса умника. Сами PDF остаются в офисной
шаре и с VPS не скачиваются. Роли индексатора и query-умника, снимок в S3 и
запуск сервиса — в [ARCHITECTURE.md](../ARCHITECTURE.md) и
[umnik/SETUP_QUERY.md](../umnik/SETUP_QUERY.md). Здесь только то, как CRM
строит запрос и что видит сотрудник.

## Где это в интерфейсе

| Место | Как открывается | Кто видит |
|---|---|---|
| Меню **Архив** | `GET /archive/?q=` | любой вошедший сотрудник, включая `designer` и `production` |
| Карточка сделки, вкладка **Согласования** | HTMX `GET /deals/<id>/archive/` при загрузке страницы | то же |
| Настройки → интеграции | URL `{UMNIK_URL}/crm/lookup`, если `UMNIK_URL` задан | только `head` / `admin` |

Вкладка согласований лежит в DOM сразу, поэтому блок архива запрашивается при
каждом открытии карточки, даже если вкладку не нажимали. Этот запрос отдельный:
если умник молчит, карточка всё равно открывается, а в блоке остаётся заглушка.

PWA `/app/` этот поиск не встраивает. С телефона страница доступна прямым
адресом `/archive/`.

Настройки не проверяют, что умник отвечает. Они только показывают, задан ли URL.

## Как собирается запрос по сделке

`archive_query_for_deal` (`deals/services/umnik.py`):

1. Если заполнены и `code_client_name`, и `code_site_name` — они через пробел.
   Лишние пробелы схлопываются. Число модулей в запрос не входит.
2. Иначе одно из этих полей, если оно одно.
3. Иначе `project_code`: `_` и `-` меняются на пробел, с начала снимается
   префикс вида `3МД` / `3 МД` (регистр не важен).

Примеры, которые проверяют тесты:

| Поля сделки | Строка в lookup |
|---|---|
| клиент `Иванов`, участок `Пулково`, код `3МД-Иванов-Пулково` | `Иванов Пулково` |
| код `3МД Иванов Пулково`, имена пустые | `Иванов Пулково` |

Свободный поиск на `/archive/` отправляет строку из поля `q` как есть.
Пустой или из одних пробелов запрос умника не вызывает и показывает форму.

На странице интеграций написано «по коду сделки». В lookup уходит фамилия и
участок, а не строка `3МД-Иванов-Пулково` целиком.

## Что отвечает умник

CRM делает `GET {UMNIK_URL}/crm/lookup?query=...&limit=...`.

`_lookup_url` дописывает путь сам: база `http://host:7861`, `.../crm` и
`.../crm/lookup` дают один и тот же URL.

| Вызов | `limit` |
|---|---|
| блок на сделке | параметр не передаётся, умник берёт **5** (`LAYOUT_LIMIT`) |
| страница `/archive/` | **20** |
| потолок умника | **40** (`LAYOUT_LIMIT_MAX`); мусор в `limit` тоже становится 5 |

В каждой карточке не больше **20** комнат (`ROOM_LIMIT`). Проёмы и стены из
каталога в этот JSON не попадают.

Поля, которые рисует CRM: `object`, `name`, `version`, `title`, `area_total`,
`area_living`, `room_counts`, `rooms[].name`, `rooms[].area_m2`, `path`.

- На карточке заголовок — `name` (имя файла без расширения). `title` не показывается.
- На `/archive/` заголовок — `object`, если он есть, иначе `name`, и рядом `title`.
- `area_total` / `area_living` — суммы площадей комнат в строке листа.
  Жилая сумма не включает помещения, в имени которых есть терраса, крыльцо,
  гараж, балкон, навес или веранда. Это не отдельное поле «площадь застройки».
- `path` — текст пути из индекса (обычно офисный `D:\Общая_Рабочая\...`).
  Ссылки на скачивание нет.

Если по таблицам листа ничего нет, query-умник добирает файлы поиском по
индексу и отдаёт их через `file_as_layout`: есть путь и имя, площади пустые.
В интерфейсе это строка «Площадь в таблицах не размечена».

Запрос с комнатами или площадью («3 спальни», «более 120 м²») на стороне умника
идёт в программный поиск листа, а не только по словам фамилии. Короткие вопросы
про состав дома удобнее писать в чат умника: страница архива только показывает
список листов.

## Доступ к порту 7861

`GuardMiddleware` пускает только loopback и частные адреса. Из интернета ответ
`403` «Только локальная сеть».

Токен:

- с **loopback** (`curl` на хосте к `127.0.0.1:7861`) заголовок не требуется,
  даже если `MCP_TOKEN` задан;
- с адреса Docker-моста (так CRM ходит на `host.docker.internal`) нужен
  `Authorization: Bearer <MCP_TOKEN>`, если токен в `umnik/.env` не пустой;
- CRM подставляет `UMNIK_TOKEN` только когда он не пустой.

`UMNIK_TOKEN` и `MCP_TOKEN` должны совпадать. Пустой `UMNIK_TOKEN` при
заданном `MCP_TOKEN` даёт умнику `401`, а в CRM — ошибку `http_401` и ту же
заглушку, что и при падении сервиса.

Проверка с хоста VPS:

```bash
curl -sS "http://127.0.0.1:7861/crm/lookup?query=Иванов%20Пулково&limit=5"
```

Проверка тем же путём, что контейнер `app` (база без суффикса `/crm`, как в `.env.example`):

```bash
docker compose exec app python -c "import os,urllib.request; url=os.environ['UMNIK_URL'].rstrip('/')+'/crm/lookup?query=test&limit=1'; req=urllib.request.Request(url, headers={'Authorization':'Bearer '+os.environ.get('UMNIK_TOKEN','')}); print(urllib.request.urlopen(req, timeout=3).read()[:200])"
```

Таймаут CRM — `UMNIK_TIMEOUT`, по умолчанию **3 секунды**. Чат умника живёт
отдельно (`UMNIK_CHAT_TIMEOUT`, 180 с) и этот поиск не удлиняет.

## Ошибки в интерфейсе

`fetch_archive` не бросает исключение на карточку.

| `archive.error` | Когда | Что видит сотрудник |
|---|---|---|
| пусто, `layouts` пуст, запрос пуст | форма `/archive/` без `q` | приглашение ввести запрос |
| `not_configured` | `UMNIK_URL` пустой | «задайте UMNIK_URL» |
| `http_<код>` | HTTP-ошибка, в том числе 401/403/503 | «Архив сейчас недоступен» |
| `unreachable` | таймаут, обрыв, битый JSON | то же |
| `bad_payload` | тело не объект | то же |
| пусто и `layouts` пуст | умник ответил, листов нет | «нет таблиц / нет файлов» и текст запроса |

Текст ошибки умника (`error` в JSON при 503) CRM не показывает: для не-200
сохраняется только код. На `/archive/` в этой заглушке ещё написано запустить
`start.bat` — это подсказка локальной разработки. На VPS сервис —
`ch-crm-umnik` (см. SETUP_QUERY).

Журнал ChangeLog и domain events поиск не пишет.

## Пример

Сделка `3МД-Иванов-Пулково`, в коде клиента и участка те же слова:

1. Открыть карточку. Вкладка «Согласования» уже заказала lookup `Иванов Пулково` без `limit` — до 5 листов.
2. Меню «Архив», запрос `Иванов Пулково` — до 20 листов, в заголовке имя объекта.
3. Запрос `6МД` на странице архива ищет шесть модулей. Блок на сделке так не делает: префикс `6МД` из кода он как раз отрезает.
