# Клиентский портал: вход, сообщения и файлы

## Назначение и границы

Портал даёт клиенту отдельный чат по сделке без учётной записи Django. Сотрудник
открывает или копирует ссылку из карточки сделки, а клиент входит по email и
паролю, заданным для связанного `Client`.

Основные компоненты:

- маршруты и обработчики: `core/urls.py`, `deals/views.py`;
- сессии: `deals/client_portal.py`, `DealClientPortalSession`;
- сообщения: `DealClientMessage`, `DealClientMessageAttachment`;
- файлы: `ProjectFile`, `deals/services/storage_paths.py`;
- интерфейс: `templates/client_portal/` и
  `templates/includes/deal_client_messages_block.html`.

## Подготовка доступа

1. При создании лида через форму на дашборде укажите email и пароль портала.
   Email обязателен, пароль должен содержать не менее 6 символов.
2. Пароль сохраняется только как Django-хеш в `Client.portal_password_hash`.
3. В карточке сделки, в блоке «Сообщения от заказчика», скопируйте абсолютную
   ссылку вида `/deals/<deal_id>/client-portal/`.
4. Для существующего клиента пароль можно установить или сменить в Django
   Admin. Обычная форма редактирования клиента поле пароля не показывает.

Одна запись `Client` хранит один пароль, поэтому связанные с ней сделки
используют одинаковые учётные данные. При этом ссылка и сессия относятся к
конкретной сделке.

## Сценарий входа

1. `GET /deals/<deal_id>/client-portal/` показывает форму email + пароль.
2. Форма отправляет `POST` на
   `/deals/<deal_id>/client-portal/send-otp/`.
3. Обработчик сравнивает email без учёта регистра с email связанного клиента и
   проверяет пароль через `Client.check_portal_password()`.
4. После успешной проверки создаётся `DealClientPortalSession`, а браузеру
   выдаётся cookie `client_portal_token`.
5. Защищённые страницы проверяют cookie для этой сделки и перенаправляют на
   форму входа, если активная сессия не найдена.

Несмотря на имя маршрута `send-otp`, текущий поток **не отправляет и не
проверяет одноразовый код**. Модель `DealClientPortalOtp`, email-настройки для
OTP и шаблон `client_portal/verify.html` остались заделом: обработчика
`client_portal_verify` в `core/urls.py` нет. Интеграции и инструкции для
клиентов не должны обещать OTP до появления отдельной реализации.

### Параметры сессии

- Срок действия фиксирован: 7 дней с момента входа.
- В БД хранится `salt$sha256`, исходный токен находится только в cookie.
- Cookie имеет `HttpOnly`, `SameSite=Lax`; `Secure` включается, только когда
  Django считает запрос HTTPS.
- Обращение к порталу обновляет `last_seen_at`, но не продлевает `expires_at`.
- Проверка перебирает не более 50 самых новых неистёкших сессий сделки.

Явного выхода, сброса пароля и отзыва всех сессий в пользовательском
интерфейсе сейчас нет. Смена пароля не удаляет уже выданные сессии.

## Маршруты

| Метод и путь | Назначение | Проверка доступа |
|---|---|---|
| `GET /deals/<id>/client-portal/` | Форма входа | Публичный |
| `POST /deals/<id>/client-portal/send-otp/` | Вход по email + пароль | Данные `Client` |
| `GET /deals/<id>/client-portal/chat/` | До 200 сообщений по сделке | Сессия портала |
| `POST /deals/<id>/client-portal/messages/send/` | Текст клиента | Сессия портала |
| `POST /deals/<id>/client-portal/messages/upload/` | Файл или голосовое клиента | Сессия портала |
| `GET /deals/<id>/client-portal/files/<file_id>/open/` | Просмотр файла | Сессия, та же сделка, файл не архивирован |
| `POST /deals/<id>/client-messages/send/` | Текст сотрудника | Django login, не file-only role |
| `POST /deals/<id>/client-messages/attach-existing/` | Файл из сделки | Django login, не file-only role |
| `POST /deals/<id>/client-messages/upload/` | Новый файл сотрудника | Django login, не file-only role |

Публичная форма до входа показывает код проекта и имя клиента. Ссылку следует
считать чувствительной, хотя для доступа к чату всё равно нужен пароль.

## Сообщения, вложения и события

Все сообщения хранятся в общей ленте сделки:

- клиентское сообщение получает `author_type=client`, email берётся из сессии;
- сообщение сотрудника получает `author_type=staff` и ссылку на Django user;
- вложение всегда ссылается на `ProjectFile`;
- `audio/*` по заявленному MIME-типу становится вложением `voice`, остальные
  загрузки — `project_file`.

Файлы записываются относительно `CRM_FILES_ROOT`:

| Источник | `ProjectFile.source` | Каталог сделки |
|---|---|---|
| Файл клиента | `client` | `incoming/client/docs` |
| Голосовое клиента | `client` | `incoming/client/voice` |
| Загрузка сотрудника для клиента | `system` | `outgoing/client` |
| Существующий файл сделки | Без изменения | Исходный путь файла |

Имена очищаются от `/` и `\` и получают префикс с временем и источником. Для
портальных загрузок категория всегда `other`; тип голоса определяется только
по MIME-типу запроса.

Отправка сотрудником текста или вложения создаёт domain event
`client_message.sent`. Сообщения и загрузки клиента такого события сейчас не
создают, поэтому обработчик этого события не является уведомлением о входящих
сообщениях.

## Эксплуатация и диагностика

Хранилище `CRM_FILES_ROOT` должно существовать или создаваться процессом
приложения и быть доступно ему на запись. Для очистки истёкших сессий очередь
должна содержать job `cleanup_expired_portal_access`, после чего запускается:

```bash
docker compose exec app python manage.py run_platform_jobs
```

Пример ручной постановки cleanup job:

```bash
docker compose exec app python manage.py shell -c \
  "from system_settings.services import enqueue_platform_job; enqueue_platform_job(job_type='cleanup_expired_portal_access')"
docker compose exec app python manage.py run_platform_jobs
```

Автоматическое периодическое создание этой job и отдельный worker в
репозитории не настроены.

Типовые проверки:

- вход возвращает «Клиент не привязан к сделке» — у `Deal.client` нет клиента;
- «Неверный email или пароль» — email не совпадает или
  `portal_password_hash` пуст/не принимает пароль;
- после успешного входа снова видна форма — проверить наличие cookie, срок
  `DealClientPortalSession` и корректное распознавание HTTPS приложением;
- файл есть в БД, но не открывается — проверить `relative_path`,
  `CRM_FILES_ROOT`, наличие файла на диске и `is_archived`.

## Текущие ограничения

- Нет rate limiting или блокировки после неудачных попыток входа.
- Нет портальной проверки расширений или размера файла; применимы только общие
  ограничения Django/reverse proxy.
- Маршрут открытия разрешает любой неархивированный `ProjectFile` той же
  сделки, а не только файл, прикреплённый к сообщению.
- Чат выбирает первые 200 сообщений в хронологическом порядке; при более
  длинной истории новые сообщения не попадут в выборку.
- Нет статусов прочтения, push/WebSocket-обновления и domain event для
  клиентской стороны.
- Модели портала и сообщений не зарегистрированы в Django Admin; пароль
  клиента меняется через admin-форму `Client`.
