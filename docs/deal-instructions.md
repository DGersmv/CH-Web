# Кто просил: журнал указаний по сделке

Журнал отвечает на вопрос «кто и когда попросил именно это», отдельно от статуса пункта и от того, кто поставил галочку.

Запись — `DealInstruction` (`deals/models.py`). Пишет её `deals/services/instructions.py` (`record_instruction`). На экране логин берётся из `actor_username`, а если поле пустое — из `requested_by.username`. Имя и фамилия профиля сюда не подставляются: у пользователя `admin` с фамилией «Пушкин» в журнале будет `admin`.

Удаление пользователя обнуляет `requested_by` (`SET_NULL`), логин в `actor_username` остаётся. Удаление пункта согласования, раздела проектирования или задачи удаляет связанные указания (`CASCADE`).

Отдельного события аудита на саму запись нет. Смена статуса по-прежнему пишется в `ChangeLog` (`approval.<slug>` / `design.<slug>`) и в `AuditEvent`, но это другая лента — «История статуса» и Главная, не «Кто просил».

## Где видно

| Место | Что показывает |
|---|---|
| Колонка «Кто просил» в чек-листе согласований и в разделах проектирования | Только последнее указание: логин и дата, без текста |
| Карточка пункта `/deals/<id>/approvals/<slug>/` и раздела `/deals/<id>/design/<slug>/` | Блок «Кто просил»: до 30 последних записей (новые сверху), источник и текст |
| Строка задачи на карточке сделки и в `/tasks/` | «Кто поставил: `<username>`» с `Task.requested_by`, не из журнала |
| Django admin `DealInstruction` | Все строки, включая производство |
| Ответ умника `summaries.approvals` / `summaries.design` и payload пункта согласования | `requested_by`, `requested_at`, у пункта ещё `last_instruction` |

Роли `designer` и `production` на страницы согласований и проектирования получают 403, журнала там не видят. Создать задачу на сделке может любой вошедший сотрудник: `POST /deals/<id>/tasks/new/` проверяет только логин.

## Что пишет строку

Пустой текст не пишется. Повтор той же строки тем же логином по тому же объекту не плодит копию: сравнивается последнее указание этого пункта / раздела / задачи, текст после `strip` и `casefold`.

| Откуда | `kind` | `source` | Текст записи |
|---|---|---|---|
| Сохранение карточки пункта, поле «Рабочие заметки» изменилось и не пустое | `approval` | `form` | Весь новый текст заметок |
| `PATCH /api/umnik/deals/<id>/approval/` с `append_note` или сменой `notes` | `approval` | `chat` | Сама дописанная строка, либо целиком `notes`, если `append_note` нет |
| Сохранение карточки раздела, поле заметок изменилось и не пустое | `design` | `form` | Весь новый текст заметок |
| Умник кладёт файл в раздел (`POST /api/umnik/deals/<id>/design-file/`) | `design` | `chat` | Имя файла |
| Создание задачи на сделке | `production` | `task` | Заголовок задачи |

Пример из чата. Сотрудник `admin` просит дописать фасад. Умник вызывает `crm_update_approval` → CRM:

```http
PATCH /api/umnik/deals/15/approval/
Authorization: Bearer <UMNIK_TOKEN>
X-Umnik-Actor: admin

{"slug":"finishing","append_note":"Фасад — планкен, краска 5071 RAL","status":"waiting_client"}
```

В пункте `finishing` появляется одна строка заметок и одна запись журнала: логин `admin`, источник «Чат», текст ровно этой строки. Повтор того же `append_note` не меняет заметки (`changed: false`) и вторую запись не создаёт. В колонке «Кто просил» будет `admin` и время; «Кто отметил» при статусе `waiting_client` останется пустым — решение ещё не принято.

На карточке то же самое делает поле «Рабочие заметки по проекту», не поле «Комментарий / файл-основание». Комментарий, статус, версия и прикреплённый с карточки файл журнал не пополняют.

## Производство

При создании задачи `requested_by` становится текущим пользователем, если поле пустое (в форме его нет). Рядом пишется `DealInstruction` с текстом заголовка. В списке задач подпись «Кто поставил» — это логин постановщика. Исполнителя в выпадающем списке можно видеть по ФИО, постановщика — нет.

Журнал производства на карточке не рисуется: `attach_latest_instructions` для задач никто не вызывает. Смотреть строки можно в админке. Отметка «выполнено» указание не меняет.

## Что умник читает обратно

`GET` карточки сделки кладёт в каждый пункт согласований и проектирования:

```json
{
  "slug": "finishing",
  "notes": "Фасад — планкен, краска 5071 RAL",
  "requested_by": "admin",
  "requested_at": "2026-10-12T16:05:00+00:00"
}
```

После `PATCH` approval в `approval.last_instruction` та же запись целиком: `id`, `kind`, `source`, `source_label` («Чат» / «Карточка» / «Задача»), `text`, `requested_by`, `requested_at`.

Актор — активный пользователь с логином из `X-Umnik-Actor`. Роль без права менять сделки (`designer`, `production`) на `PATCH` approval получает 403, запись не создаётся. Файл в раздел проектирования умник может положить любым активным сотрудником (`can_attach_design_files`): тогда «Кто просил» — его логин, текст — имя файла. Повтор того же имени в тот же раздел файл не копирует заново, но указание пишется (или возвращается уже существующее, если текст и логин те же).

Загрузка файла кнопкой «Прикрепить» на странице раздела событие `deal.design_file_added` пишет, а `DealInstruction` — нет. Колонка «Кто просил» после такой загрузки не меняется.

## Ограничения

- Правка заметок на карточке кладёт в журнал весь текст поля, а не разницу. Дописать одну строку, не затерев историю формулировок, умеет только `append_note`.
- Очистка заметок запись не создаёт и старые не удаляет. Подсказка «есть рабочие заметки» гаснет, колонка «Кто просил» остаётся.
- На карточке пункта и раздела видны 30 последних строк. Остальное — в админке.
- Сравнение повтора не склеивает пробелы внутри строки, только края и регистр.
- Дедуп смотрит только на последнюю запись этого объекта. «А, потом Б, потом снова А» — три строки.
- Указания не попадают в ленту Главной.
