# Движок обзорной сметы

`calculate_config` считает строки 4–43 листа «Таблица обзорная» и кладёт результат в `ProjectVersion.frozen_data['calculation']`. Схема — `excel-v1` (`CALC_SCHEMA_VERSION`).

Страницы конфигуратора в браузере сейчас выключены (см. ниже). Карточка сделки всё равно считает смету в памяти и не сохраняет её. Умник `update_config` / `update_cost` пишет JSON и флаг не проверяет. Пересчёт после санузлов и доп. опций выполняется только когда эти страницы включены.

## Два прайса

| Что меняете | Куда попадает в итог |
|---|---|
| Цена в `/settings/catalog/` у позиции **без** секции `bathroom_template_v1` / `additional_options_template_v1` | Никуда. Обзорка эти `CostItem` не читает. |
| `formula_multiplier` на `CostItem` | Никуда. Поле хранится и редактируется, код его не вычисляет. |
| Цена шаблона санузла или доп. опции | Только в **новые** строки версии. Уже созданная строка держит свой `unit_price`. |
| Литералы в `calculate_config` (`deals/services/calculation_engine.py`) | Строки обзорки при следующем полном пересчёте. |

`seed_demo_data` тоже пишет `CostItem.price_material` / `price_work`. На обзорку это не влияет.

Санузел и доп. опции — отдельные сервисы (`deals/services/bathrooms.py`, `deals/services/additional_options.py`). Здесь только то, как их суммы входят в обзорку.

## Кто вызывает

| Вход | Пишет `frozen_data` | Условие |
|---|---|---|
| `GET /deals/<id>/` (`DealDetailView`) | Нет. Если черновика нет — создаёт пустой `ProjectVersion`. Если `calculation` ещё нет, считает в памяти от сохранённых `config_inputs` или от дефолтов формы (120 м² и т.д.) и **не сохраняет**. | Карточка этот блок не рисует (`deal_detail.html` не включает `deal_cost_panel.html`). |
| `POST /deals/<id>/config/save/`, сохранение на `/deals/<id>/cost-summary/` | Да, полный пересчёт. | Страница отдаёт ответ только при включённом конфигураторе. |
| `POST /deals/<id>/config/recalc/` | Нет, кусок HTML. | То же. |
| `POST /deals/<id>/cost-summary/update/` | Правит только `calculation.totals`. Строки не пересчитывает. | То же. Отрицательные суммы — 400. |
| `POST` сохранения санузла или доп. опций | `_recalc_draft_calculation`, если в черновике уже есть `config_inputs`. Без них выходит сразу. | Страницы за флагом. |
| Умник `update_config` | Да, тот же полный пересчёт, что save. | Флаг конфигуратора **не проверяется**. Нужен `can_edit_deals` (не проектировщик и не производство). Поля, которые не передали, берутся из черновика или из дефолтов формы (120 м² и т.д.) и записываются. |
| Умник `update_cost` | Как ручные итоги: подменяет `totals`, строки не трогает. | То же. |
| Смена `margin_percent` (`POST /deals/<id>/margin/` и умник `update_deal`) | Нет. Пишет `Deal.margin_percent` и `ChangeLog`. | Старый `with_margin` в JSON остаётся, пока не будет полного пересчёта. |

Новая сделка (`DealCreateView`, лид с дашборда) получает `margin_percent` из `SystemConfig.default_margin_percent` (пустое значение → `30`). Позже правка настройки старые сделки не обновляет.

## Что лежит в JSON

Полный save (`save_configurator_draft` и умник `update_config`) **заменяет** `frozen_data` целиком:

```json
{
  "calc_schema_version": "excel-v1",
  "config_inputs": {},
  "calculation": {},
  "saved_at": "2026-10-26T12:00:00+00:00"
}
```

Пропадают ключи, которые лежали в том же черновике: `objects` и `contract_version` от `POST /api/plugin/project-versions/`, `electrical` со страницы электрики. Колонка `plan_pdf_path` при этом не стирается — она не в JSON.

Плагин создаёт **новую** версию со статусом `draft`. Черновик для расчёта — последний по `version_number`. Сохранение сметы после импорта ArchiCAD затирает `objects` этой версии.

`calculation` перед записью прогоняется через `_json_ready`: `Decimal` становится `float`.

Ручной `update_cost` / `cost-summary/update` не создаёт `calc_schema_version`, если его не было. `ChangeLog`:

- смена входа — `config.<имя поля>`;
- ручные итоги — `cost_summary_manual_edit`;
- наценка — `margin_percent`.

Отдельного `AuditEvent` на пересчёт нет.

## Входы

Форма — `DealConfiguratorForm`. Пустое / нечисловое в самом движке становится `0` (`_to_decimal`). Отрицательные режет форма (`min_value=0`), не `calculate_config`.

Денежные поля можно прислать с пробелами, `₽` и запятой. Если в числе и точка, и запятая, десятичный разделитель — тот, что правее.

Ключа `facade_lm` и `bathrooms_total_cost` нет. Фасад — два поля: `facade_planken_lm` и `facade_combined_lm`. Наполнение санузлов считается, а не вводится.

Дефолты, когда `config_inputs` ещё нет (карточка и первая отрисовка сметы): застройка 120, жилая 90, потолок 2.7, пол 200 мм = 120, ламинат 90, фасад комбинированный 48, перегородки 24 и 16, ЛДСП 48, двускатная кровля 120, двери 5, окна 8, санузлов 1, остальные нули.

## Как получается количество

Деньги: `Decimal`, `ROUND_HALF_UP` до копеек. Сначала округляется площадь, потом сумма строки `qty * price`, потом итоги.

| Площадь / количество | Формула |
|---|---|
| Планкен, комбинированный фасад | м.п. × (`ceiling_height` + 0.95) |
| Наружная стена | `facade_combined_lm` × (`ceiling_height` + 0.15). Отдельного ввода нет, планкен сюда не входит. |
| Перегородки 200 / 100 | свои м.п. × (`ceiling_height` + 0.15) |
| Отделка стен и плитка санузла | свои м.п. × (`ceiling_height` + 0.05) |
| Двускатная кровля | `roof_gable_qty` × 1.15 |
| Плоская кровля (конструктив) | `roof_flat_qty` как есть |
| Наплавка плоской кровли | тоже `roof_flat_qty`, не площадь × 1.15 |
| Натяжной потолок | `living_area` |
| Проект, кладовщики, электрика, конвекторы, расходники, упаковка, накладные | `building_area` |

Пример. Потолок 2.7, комбинированный фасад 48 м.п.: площадь = 48 × 3.65 = 175.20 м². Материал строки `facade_combined` = 175.20 × 2830, работа = 175.20 × 1200.

Сауна: количество 1, если `sauna_cost` или `sauna_installation_cost` больше нуля, иначе 0. Окна «под ключ» и панорама «под ключ» — количество 1 только когда соответствующая сумма больше нуля. Отделка окон и панорамы считается отдельно, по штукам.

## Санузлы внутри строк C33–C34

Если на версии **нет** `DealBathroom`:

- материал сантехники (`plumbing`) = **60000** за санузел;
- работа сантехники = сумма зашитого листа «вкладка 2» (`_bathroom_sheet_totals`, 14 пар qty/цена);
- материал оборудования (`bathroom_equipment`) = сумма того же листа по материалам (22 пары);
- работа оборудования = 0.

Число санузлов умножает эти единицы. Каталог тут не участвует.

Если строки санузла уже есть (`has_bathroom_data`):

- материал сантехники = **0** (чтобы не прибавить ещё 60000);
- работа сантехники и материал оборудования = суммы включённых строк версии, делённые на `bathrooms_count` из входов и снова умноженные на него (копейки на каждом шаге);
- при `bathrooms_count = 0` вклад санузлов в обзорку нулевой, даже если строки есть;
- пустые вкладки (записи есть, включённых строк нет) тоже дают ноль и **не** возвращают эталон 60000.

Снимок строки берётся при создании из опции каталога (если цена опции 0 и это не `customer_material` — из `CostItem`). Смена цены в каталоге старые строки не двигает. При сохранении вкладки, если у строки сменилась опция и `option.price > 0`, `unit_price` обновляется.

## Доп. опции

`additional_options` в ответе — отдельный объект: строки с `is_included`, материал, работа, `subtotal`. В `totals.subtotal` и `totals.with_margin` они **не входят** и наценкой не умножаются.

Кто что складывает:

- колонка «сумма» в списке сделок (`DealListView._extract_total`) — только для руководства: сохранённые `totals.with_margin` + `additional_options.subtotal`. Нет ключа `with_margin` — дальше ищутся другие пути в JSON, `agreed_price` не читается. Живой пересчёт при открытии списка не делается;
- `serialize_deal` для умника отдаёт только `calculation.totals`, без доп. опций и без договорной цены;
- карточка сделки показывает `Deal.agreed_price`. Движок это поле не читает и не пишет.

## Наценка

`with_margin = subtotal * (1 + margin_percent / 100)`, одно округление до копеек. `subtotal` — сумма материалов и работ строк 4–43, уже округлённых построчно.

## Флаг конфигуратора

```python
CONFIGURATOR_ENABLED = getattr(settings, 'CONFIGURATOR_ENABLED', False)
```

Читается один раз при импорте `deals/views.py`. В `core/settings.py` настройки нет, переменная окружения не читается. Пока флаг выключен, эти URL отвечают редиректом на карточку (HTMX — `HX-Redirect`) и сообщением про ручную договорную цену:

- `/deals/<id>/cost-summary/` и `.../update/`
- `/deals/<id>/config/save/`, `/deals/<id>/config/recalc/`
- `/deals/<id>/bathrooms/…`, `/deals/<id>/additional-options/…`
- `/deals/<id>/electrical/` и `.../save/`

Проверка флага стоит раньше проверки роли, поэтому проектировщик получает тот же редирект, а не 403. Умник флаг не смотрит.

Включить: задать `CONFIGURATOR_ENABLED = True` в settings **до** импорта views и перезапустить процесс (`daphne` сам код не подхватывает).

## Если цифра «не та»

1. Правили каталог, а обзорка старая — для строк 4–43 это ожидаемо. Меняется только литерал в `calculate_config` и следующий полный пересчёт.
2. Правили шаблон санузла — смотрите `unit_price` у `DealBathroomLine`, не текущий `CostItem`.
3. Поменяли наценку — в JSON остался прежний `with_margin`, пока не будет `update_config` / save.
4. После ручного `update_cost` итоги и строки расходятся специально: строки не пересчитывались.
5. Список руководства и ответ умника — разные суммы: список прибавляет доп. опции, умник нет. Карточка показывает договорную цену, не этот движок.
6. Импорт ArchiCAD, затем save сметы — `objects` в черновике уже нет.
7. Умник прислал одно поле конфигурации на сделку без сохранённых входов — остальные входы стали дефолтами формы и уехали в `config_inputs`.
8. `serialize_deal` с пользователем создаёт пустой черновик, если его не было, но сам расчёт не запускает. В ответе `totals` пустой, пока кто-то не сохранит `calculation`.

Проверка формул против выгрузки Excel: `build_formula_reconciliation_report` сравнивает текст формулы, не деньги, для ячеек C5, C16, C20, C33, C34 и C43. Тест читает `/app/docs/excel_extract.json` внутри контейнера.
